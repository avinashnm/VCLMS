# 3 SYSTEM DESIGN

## 3.1 Module Descriptions
The structural architecture of the Virtual Chemistry Laboratory Management System (VCLMS) is segregated into highly specialized, interoperable modules. Each module is specifically optimized to perform complex technical duties ranging from deep database administration to highly volatile 2D physics rendering on the client side.

### 3.1.1 Authentication & Role-Based Access Control (RBAC) Module
The Authentication Module operates as the primary, unyielding security gateway of the VCLMS framework. Leveraging Django’s enterprise-grade authentication middleware, this module meticulously manages user identity validation, session persistence protocols, and hierarchical access rights. It implements a sophisticated Role-Based Access Control (RBAC) mechanism designed specifically to cater to three distinct institutional profiles:
- **Head of Department (HOD) / Admin:** Granted absolute override privileges. HODs manipulate cross-department configurations, register entire batches of students, and utilize the No-Code Experiment Builder to generate global laboratory protocols.
- **Faculty / Staff Level:** Granted localized instructional permissions. Faculty members upload specific theoretical study materials, monitor real-time class attendance matrices, and audit the granular laboratory performance records of their explicitly assigned students.
- **Student Level:** Granted secured consumer-level access. Students navigate their personalized theoretical courses, initiate interactive simulation sessions, retrieve individual penalty feedback, and securely download authenticated PDF appraisal certificates.

By centralizing the identity layer over a PostgreSQL database, the system encrypts passwords using advanced hashing algorithms (like PBKDF2) and utilizes Cross-Site Request Forgery (CSRF) tokens to rigorously protect the integrity of academic records from unauthorized interception or manipulation.

### 3.1.2 No-Code Experiment Configuration Module (The Authoring Engine)
A revolutionary pillar of the system's administrative design is the No-Code Experiment Configuration Module. Historically, digital simulation parameters were strictly hardcoded, meaning modifying a chemical endpoint or validation sequence required extensive developer reprogramming. This module fundamentally decentralizes authoring power, transferring complex simulation logic entirely via a graphical User Interface (UI) into the hands of chemistry faculty.

This highly advanced module operates through a deeply structured dynamic property architecture. Faculty interact with specialized, database-driven dropdowns and robust chemical selection modals to define critical parameters—such as identifying the specific Titrant, the precise Analyte volume, and the exact Indicator required. The most sophisticated feature is its "Material Sync" logic; when an educator selects a chemical from the drop-down catalog, the module autonomously synchronizes its exact molecular nomenclature and hidden mathematical thresholds directly into the configuration payload. 

Once the educator finalizing the setup, the module serializes the entire protocol into a highly dense JSON structure, transmitting and securing it perpetually within the PostgreSQL backend. This completely bypasses the need for manual programming while ensuring unlimited scalability for designing countless chemical variations (e.g., strong acid-strong base, weak acid-strong base permutations) through one unified logic hub.

### 3.1.3 Virtual Laboratory Simulation Module (The Physics & Telemetry Engine)
The Virtual Laboratory Simulation Module serves as the technical nucleus for practical execution. Deployed utilizing the `p5.js` library, this high-fidelity geometric and mathematical engine operates concurrently within the Django front-end templates. It is responsible for instantly parsing the JSON protocols generated by the No-Code Builder and translating them into tangible, interactive 2D physics properties on the browser canvas.

Unlike legacy simulations that arbitrarily playback pre-rendered visual animations, this module processes active fluid dynamics. When a student operates the virtual burette tap, the engine continuously calculates continuous liquid subtraction from the main vessel while calculating volumetric addition to the conical flask stationed below. Furthermore, the simulation supports true realistic mechanics such as the physical overfilling of vessels or the draining of apparatus. 

Crucially, the module computes dynamic stoichiometric color transitions. By continuously monitoring the virtual pH balance and cross-referencing it with the educator-defined indicator logic, the system renders flawless, mathematical color interpolations (such as transitioning from a vibrant phenolphthalein pink immediately to a colorless threshold). This ensures entirely physically accurate visualizations, rather than arbitrary, timeframe-based color animations.

### 3.1.4 Academic Management (LMS) Module
The Academic Management Module serves as the comprehensive administrative backbone encompassing the holistic educational lifecycle. It facilitates the asynchronous delivery of dense theoretical study materials, PDF instructional protocols, and highly compressed preparatory video courses. This module enables a seamless transition to the virtual workspace; faculty can enforce prerequisites, ensuring theoretical competency is demonstrated before practical laboratory access is granted.

Beyond content delivery, the module automates immense swathes of institutional tracking. It correlates successful experimental sessions directly with student progression metrics, streamlining the daily attendance bureaucracy. It ultimately manages the secure, server-side generation of authenticated PDF Lab Appraisal Certificates—aggregating the procedural telemetry, the penalty deductions, and the mathematical calculations to forge permanent, physical evidence of the student’s academic rigor.

## 3.2 Workflow of The Proposed System
The overarching workflow of VCLMS was mathematically formulated to mirror the stringent chronological discipline of a professional physical laboratory, mandating preparation, precise execution, rigorous documentation, and ultimate computational evaluation. 

Upon successfully authenticating through the RBAC gateway, the student lands directly within the LMS hub. They absorb the essential theoretical parameters of the pending experiment. Upon engaging the laboratory session, the system queries the PostgreSQL database, retrieves the deeply structured active configuration crafted by the HOD, and boots up the `p5.js` engine—parametrically rendering the specialized apparatus and chemical parameters for that exact simulation instance.

### 3.2.1 Laboratory Execution Sub-module (Manual Assessment Pipeline)
Within the execution sub-module, the system demands exhaustive physical discipline via the interactive canvas. The student enters the setup phase, where they must precisely align their digital apparatus—dragging, dropping, and validating the burette placement, the funnel insertion, and the analyte formulation. 

The primary innovation during the titration phase revolves around the forced **"Student-Initiated Manual Assessment"** workflow. Rather than holding the student’s hand—whereby the system automatically pauses the experiment and signals that a chemical endpoint has materialized—the student must exhibit profound visual acuity. They must manually govern the titration flow rate, aggressively observe the continuous stoichiometric color shift, halt the procedure autonomously upon spotting the precise endpoint, and manually trigger the observation save. 

Concurrently running silently in the background is the overarching **Marking Manager**. This continuous telemetric proctor monitors every micro-interaction. If a student forgets to zero an initial burette reading, excessively overfills a chemistry vessel due to negligence, or attempts a titration without maintaining required flask agitation, the Marking Manager immediately logs explicit procedural faults. The simulation explicitly utilizes exact chemical name validation against the catalog, severely penalizing random guesses or technically inaccurate setups. 

### 3.2.2 Calculation & Results Sub-module (Algorithmic Verification)
Following the cessation of the practical execution sprint, the student transitions immediately into the post-experiment Calculation Sub-module. Here, the student is legally tasked with documenting their recorded initial volumes (V1) and concordant values (V2) generated strictly by their manual observations. 

They must then independently execute the advanced molarity-based mass-equivalence mathematical formulas to derive the estimated weights of the unseen chemical samples. Simultaneously, the core mathematical algorithm retrieves the absolute, hidden simulation true values established via the No-Code configuration payload. The system performs a rigorous comparative verification, granting the student’s finalized mathematical derivations against the baseline truth with a hardcoded, maximum scientific tolerance window. 

If the student's mathematical conclusions align flawlessly, maximum evaluation points are accrued. If deviations are mathematically intolerable, compounding score deductions apply. Ultimately, the calculation module merges the student's mathematical validity score alongside the granular procedural penalty log deduced by the Marking Manager. This synthesized dataset is permanently compiled into the finalized Database logging framework, rendering a final, unalterable PDF appraisal report concluding the academic transaction.
